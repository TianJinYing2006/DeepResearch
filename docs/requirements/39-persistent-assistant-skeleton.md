## 0. 一句话

把项目从「一次性研究工具」升级为「**长期研究助手**」：能**按时间持续追踪**（D）某一主题的增量变化，能**跨 run 积累**（E）用户级研究偏好与历史结论。

## 1. 方向 D —— 持续追踪（定时 / 事件触发）

| 项 | 内容 |

| 竞品参照 | Perplexity Computer Automations（调研 §1.2）：定时 + 事件触发（Slack/Gmail/Outlook/Linear/GitHub 连接器）+ 跨次运行保留历史 + 重要动作人工审核 + 等待触发不计费 |

## 3. 合并批次的框架（8~12 天，调研口径）

```
D 持续追踪：订阅模型 → 触发（cron/事件）→ 重跑 → manifest diff → 增量报告 → 通知
E 研究档案：终局摘要沉淀 → 用户级档案（偏好 + 结论）→ 新 run 规划前注入 → 作用域与删除
                              └────────── 共用：用户级预算闸 + 通知渠道（邮件基建已有） ──────────┘
```

## 7. 评审结论与立项前补充

### 7.1 合理性结论

长期研究助手的方向成立，但 D（自动触发研究）与 E（跨 run 个人记忆）在威胁模型、数据生命周期、故障处理和验收指标上不同。当前把两者并为 8-12 天批次的估算偏乐观：共同依赖预算、通知和身份治理，不代表需要同一数据模型或同时上线。建议保留 39 为路线骨架，立项时拆成两个阶段：先做用户主动启用的 D0 定时追踪最小闭环，再决定是否做 E；事件触发、自动把结论回流记忆均后置。

### 7.2 背景与 D 的边界

- **背景**：已有队列 worker 与 manifest 提供执行和比较基础，但调度订阅、触发去重、跨次基线、通知状态和预算预留是新的持久化域。cron 只是触发器，不能在 API 进程里用内存定时器实现；多副本下需由 DB 认领和幂等键防止重复创建。
- 订阅至少需要 owner、规范化主题/研究参数、profile、频率/时区、下次触发时间、暂停/过期状态、单次与周期预算、最近成功基线 run、连续失败计数、通知偏好和创建来源。保存创建时的参数快照，后续修改要产生新版本；不得默默使用当前默认配置改变订阅含义。
- 每次触发先做预算预留与幂等去重，预算不足时暂停并通知，不创建研究 run。单次执行成本从 usage ledger 汇总；空触发/等待调度不计模型费，但调度、检索及通知成本要分别定义。
- manifest diff 只比较相同订阅版本、规范化研究范围和证据身份口径。新增、内容变化、来源更新可报告；上一轮缺失不能直接解释为来源删除/事实失效。任何“消失”结论需单独验证，不能从抓取波动推断。
- v1 仅 cron，不接外部事件源；无变化可静默但要有健康状态/连续失败提醒，避免静默等同于任务已正常运行。

### 7.3 背景与 E 的隐私边界

- **背景**：RAG scope 可提供租户隔离原语，但个人记忆不是普通检索文档。写入错误会在后续研究持续污染结论；读取越权会造成跨 run 数据泄漏。因此首版应把明确偏好与事实性研究结论分开。
- 先只支持用户可查看、编辑、删除的显式偏好（如引用语言/来源偏好），不自动将模型生成结论写成长期记忆。将来引入结论档案时，记录来源 run、证据 ID、生成时间、有效期、置信/状态和撤销链；新 run 注入时必须展示或可追溯，并由用户控制是否启用。
- 记忆不作为 critic 的事实依据；只能作为计划偏好或待验证线索。引用与事实判断必须回到本次 run 可验证的证据池。用户注销、删除记忆和删除源 run 的级联/保留策略须在 schema 前确定。
- 需求 36 的 follow-up 是单 run、只读既有证据；跨 run memory 是用户级长期数据。不得用共享向量库或同一检索 filter 混为一个“上下文”入口。

### 7.4 建议实施策略

1. **D0 发现/演练**：先做只读调度设计和预算模型，确定订阅生命周期、时区/夏令时、幂等、暂停/删除、失败通知及成本上限；用 fake clock 和重复 worker 认领演练，不调用真实模型。
2. **D1 内测**：实现 cron-only、每个订阅最多一个在途 run、manifest 增量报告、明确暂停/预算不足状态；小范围手动创建订阅，观察重复触发、无变化比例、增量质量和成本后再扩大。
3. **E0 单独立项**：先做显式偏好 CRUD、用户导出/删除与 plan 前注入审计；以跨用户隔离、删除完成和默认关闭作为上线门槛。事实结论记忆需单独研究评测与新需求，不跟随 E0 自动上线。
4. 只有 D0 与 E0 都稳定且用户明确需要，才评估事件触发、自动结论沉淀或重要变更的 HITL 审批；逐项复用 36 的人审事件协议，不把自动化权限等同于人工批准。

**重新估算建议**：D0/D1 与 E0 分开估时；原 8-12 天只可作为代码实现的粗略下界，不含预算政策确认、删除与隐私审查、重复触发演练、增量质量评测及线上观察期。当前状态继续保持「骨架、未立项」，不据此安排实现。

### 7.5 同类项目对照与证据边界

- [GPT Researcher README](https://github.com/assafelovic/gpt-researcher) 提到研究期间维护 memory/context，并通过其 MCP server 分开提供来源和完整上下文读取。这能说明研究型 Agent 常把研究结果与上下文读取作为不同能力；README 并未证明这是跨 run、按用户隔离且具有删除/遗忘语义的长期记忆，因此不能据此直接决定本项目的 E 方向实现。
- [GPT Researcher MCP Server](https://github.com/assafelovic/gptr-mcp) 将深度研究、快速搜索、报告生成、来源获取和完整上下文获取拆成工具。对本项目的启示是可组合的外部接口不等于应暴露所有内部状态：来源清单可提供分页和权限校验，完整上下文仍应保留为受限能力。
- 自动化竞品的“等待触发不计费”只适用于尚未启动研究的等待阶段；不能推导为触发后的搜索、LLM 与通知都不计成本。需求 39 应继续以订阅预算和实际 usage ledger 为准。
