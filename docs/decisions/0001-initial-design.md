# ADR-0001：初始架构与核心设计策略

## 基本信息

- **编号**：0001
- **标题**：初始架构与核心设计策略
- **日期**：2026-08-19
- **状态**：已采纳
- **涉及模块**：全部

## 背景

本项目是求职 Agent 开发实习生的第二个项目，与已有的 wechatbot（微信多 Agent 穿搭助手）形成互补。目标：三者兼顾（求职含金量 / 真实可用 / 学习驱动），以求职为第一优先级。

## 核心设计决策

### 1. 项目定位：聚焦核心链路的深度 MVP

不做完整产品（Web UI、用户系统、任务队列等外围功能），聚焦核心链路：规划 → 多跳检索 → 交叉验证 → 生成报告。用 CLI + 轻量 Web UI 交互，把精力集中在核心 Agent 编排的深度上。

#### 1.1 修订（2026-09-20，W9）：「轻量 Web UI」的边界解释

W9 将 Web UI 从 Streamlit 迁移到 **FastAPI + React/Vite**（详见
`docs/requirements/9-web-ui-rewrite.md`）。本修订**不推翻**上述定位，只把「轻量 Web UI」
进一步解释为：

> **允许升级呈现层技术栈，但不扩展产品边界。**

即：**「用什么做」可以升级，「做什么」不得扩展。**

**允许**：引入前端构建链（Vite + React + TypeScript + Tailwind）作为**呈现层**；
后端 SSE 事件流对齐 AG-UI 语义（但不引 CopilotKit）。

**明确不做**（沿用原 ADR，此处固化为可检查项）：登录、用户系统、任务队列、任务持久化、
多租户、权限、云端部署。任务模型仍为**前台运行**。

**三条硬边界**：

1. **前端不承载研究逻辑** —— 前端只做「展示状态 / 提交配置 / 发送取消请求」，
   不得复制或实现 `research_engine/` 的任何判定逻辑。可写成 CI 检查：
   前端目录不得 import `research_engine`。
2. **不引入产品化功能** —— 见上「明确不做」清单。
3. **W9 完成标准封顶** —— 只实现：提交研究、实时阶段进度、降级事件展示、
   token/cost 展示、取消、报告与引用展示、文档摄取状态。
   **不做**聊天框、复杂工作台、历史任务中心、CopilotKit。

**取消契约**（W9 拍板）：采用**节点边界上的协作式取消** —— 取消请求立即生效；
执行停止在下一个安全边界；当前同步节点允许自然结束；**取消后不再启动新的研究节点与
LLM 调用**。最坏等待 = 当前节点剩余执行时间（实测估算量级为**数十秒**，见需求文档 §5.4.1）。
⚠️ 不追求毫秒级强杀：`graph.stream()` 是同步生成器且 Python 无法强杀线程，
这是**语言级限制，与前端选型无关**，不应归咎于所选前端框架。

**与 §理由与取舍 的一致性**：原 ADR 的理由是「面试官最看重核心编排深度和可量化结果，
而非 UI 完整度」。W9 只升级呈现层、不动核心链路与任务模型，因而**与该理由不冲突** ——
UI 仍不是本项目卖点，只是不再成为短板。**W9 不修改 `research_engine/` 的核心判定口径。**

### 2. 核心卖点

- **主卖点**：多跳检索 + 交叉验证防幻觉
- **副卖点**：多源检索融合（网络 + RAG 私有知识库）
- **技术底座**：LangGraph 状态机编排
- **加分项**：成本优化（三层 LLM 分级 + 动态路由）

### 3. 多跳检索设计

- Planner 将研究问题分解为子问题
- Researcher 对每个子问题执行动态多跳检索
- 基于"信息充分度"判断是否继续（上限 5 跳防死循环）
- 融合网络搜索（博查）+ RAG 私有知识库

### 4. 交叉验证（防幻觉）

- **引用存在性校验**：报告中的引用是否真实存在于检索结果
- **多源交叉印证**：关键论断需多个独立来源支持，输出置信度分级
- 内容一致性校验（论断与引用原文语义比对）作为可选增强，不纳入 MVP 核心

### 5. RAG 进阶链路

- 支持多格式文档上传（PDF/Word/Markdown/TXT）
- 混合检索（向量 + BM25）
- 分块优化
- rerank 默认关闭，先立评测再决定去留（借鉴 wechatbot 的 rerank 负收益经验）
- 复用 wechatbot 的评测方法论（真实查询 + 命中率评测）

### 6. 评测体系

- **A 检索命中率**：复用 wechatbot 方法论
- **B 引用准确率**：主卖点量化（存在性 + 多源印证）
- **C 报告质量**：LLM-as-judge（借鉴 RACE 四维度）
- **D 端到端验收**：跑真实研究主题

### 7. 技术栈

- **LLM**：阿里云百炼 Qwen（初始 qwen-turbo/plus，可配置切换）
- **三层 LLM 分级**：fast（摘要）/ smart（写作）/ strategic（规划）
- **向量库**：Qdrant（复用 wechatbot 经验）
- **Embedding**：百炼 text-embedding-v3
- **网络搜索**：博查（可切换 Provider）
- **编排**：LangGraph

### 8. 架构借鉴

- **LangChain open_deep_research**：上下文隔离、渐进式压缩、RACE 评测
- **gpt-researcher**：三层 LLM 分级、成本追踪、多检索器可插拔
- **dzhng/deep-research**：breadth/depth 参数化控制成本
- **Validator 是差异化亮点**：主流 DeepResearch 项目普遍缺失图内 Validator 节点

## 理由与取舍

- **为什么聚焦核心链路**：面试官最看重核心编排深度和可量化结果，而非 UI 完整度；已有 wechatbot 证明完整产品能力，本项目差异化展示编排深度
- **为什么用便宜模型**：成本优先，初始全用 qwen-turbo/plus，后续可单独升级 strategic 到 qwen-max
- **为什么 Validator 用图内节点**：主流实现靠评测闭环而非图内验证，本项目将其作为防幻觉核心，是差异化亮点
- **为什么 Qdrant 懒加载**：图构建不依赖外部服务，Qdrant 不可用时优雅降级，不影响网络搜索主链路

## 影响

- 全部模块按此设计实现
- 后续优化需遵循本 ADR 的决策链
