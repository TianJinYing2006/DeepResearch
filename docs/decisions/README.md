# 设计决策记录（ADR）

本目录记录 DeepResearch 项目的**设计决策**与**修改背景**，作为项目记忆。

## 为什么要有这个目录

- **决策有据可依**：每个关键设计决策记录“背景、方案、理由、取舍”，避免遗忘或重复讨论。
- **修改先讲背景**：修复 bug / 优化设计时，先说明“当时为什么这么设计”，再说明“现在为什么改”，形成完整决策链。
- **可追溯**：面试或复盘追问“为什么这么设计”时，能讲出完整决策过程与代价。

## 规范（2026-10-26 修订，与 `CONTRIBUTING.md` §5 一致）

1. **一个决策一个文件**，命名 `NNNN-短横线标题.md`，编号唯一递增。
2. **何时必须写**：架构级改动、线上缺陷修复、改判定/指标口径、产品边界或阶段变化、删除公共模块/API/配置项。
3. **何时可免**：局部实现细节、文案与样式、补充测试、默认值微调（PR 说明即可）。
4. **内容七段**（见 [TEMPLATE.md](TEMPLATE.md)）：基本信息 / 背景 / 问题动机 / 方案 / 理由与取舍 / 影响 / 变更记录；必须写“放弃的方案 + 代价”。
5. **状态** ∈ 草稿 / 已采纳 / 已取代 / 已废弃；被取代必须交叉链接，禁止静默失效。
6. **索引必须同步**：新增或改变状态后，更新本文件索引表（编号、标题、状态、日期）。
7. **编号冲突**：发现重号时，按“后到者改号”修正，并在索引与文件变更记录中注明；不删除历史文件。
8. **与需求文档互链**：ADR 记录决策，需求文档记录设计与 DoD；同一决策不得双写两份互相漂移的版本。

## 新增 ADR 流程

1. 复制 [TEMPLATE.md](TEMPLATE.md) 为 `docs/decisions/NNNN-slug.md`（NNNN = 当前最大编号 + 1）；
2. 写清背景 / 问题 / 方案 / 取舍 / 影响；
3. 更新本文件索引表；
4. 在对应需求文档的「变更记录」追加一行并互链；
5. 随代码/文档改动走同一分支 + PR（治理类改动需主理人确认）。
