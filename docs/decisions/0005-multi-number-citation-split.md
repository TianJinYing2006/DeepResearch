# ADR-0005：多编号引用拆分（鲁棒的引用协议解析）

## 基本信息

- **编号**：0005
- **标题**：多编号引用拆分（鲁棒的引用协议解析）
- **日期**：2026-08-20
- **状态**：已采纳
- **涉及模块**：`research_engine/agents/validator.py`

## 背景

ADR-0002 建立编号引用协议时，Writer 的提示词要求输出 `[来源: N]` 单编号形式。但 LLM 实际输出并不总遵守：实测 67 条引用仅 17 条通过校验，其中相当一部分是 Writer 输出了 `[来源: 5, 72, 77]` 这类**多编号引用**（一个论断由多个发现共同支持，这在语义上是合理甚至更优的写作行为）。

旧提取逻辑：

```python
pattern = r"\[来源:\s*([^\]]+)\]"
citations.append({"claim": claim, "source": m.group(1).strip()})
```

正则捕获组把 `5, 72, 77` 当成**一个整体字符串**，`index.get("5, 72, 77")` 必然 miss，且降级为存在性校验后 `verified=False`——校验器把"合法的多编号引用"误判为"编造引用"。

## 问题 / 动机

1. 引用通过率被系统性低估（校验器的失败 ≠ Writer 的错），主卖点的量化指标失真
2. 多编号引用本是合理输出，却被协议层惩罚——正确的做法是**扩展协议**而非收紧提示词禁止
3. 中文场景下 LLM 还会输出 `[来源: 5、8]`、`[来源: 3和7]` 等中文分隔符变体

## 方案

在 `Validator._extract_citations` 中增加拆分逻辑：正则捕获后，若内容**全部为纯数字 token**，则按中英文分隔符拆分为多条独立引用，每条单独做存在性校验：

```python
tokens = [t for t in re.split(r"[,，、;；/和\s]+", ref.strip()) if t]
if len(tokens) > 1 and all(re.fullmatch(r"\d+", t) for t in tokens):
    return tokens        # 多编号：拆分
return [ref.strip()]     # 单一来源（编号或 URL）：原样返回
```

效果：`[来源: 5, 72, 77]`（假设共 10 条发现）→ 3 条独立引用，`5` verified=True，`72`/`77` 越界 verified=False。**多编号中的越界编号现在能被单独暴露**，而旧逻辑下整串失败，无法区分"全错"和"部分错"。

## 理由与取舍

- **为什么在 Validator 侧拆而不是改 Writer 提示词禁止多编号**：多编号引用是好行为（多源支持一个论断，正是多源印证想要的形态）。禁止它是在削足适履；正确的方向是让校验端理解更丰富的合法协议
- **为什么要求"全部 token 都是数字"才拆**：协议还兼容 `[来源: <真实URL>]` 形式。若 `5, https://example.com/x` 被拆开，URL 会失去"5"的上下文导致误判。混合内容整体视为单一来源（保守处理，宁可 verified=False 也不误标 verified=True）
- **为什么不扩展编号区间（如 [来源: 5-8]）**：区间展开会放大 LLM 编造编号的影响面（一个编造区间 = 4 条假引用），且实测中区间形式罕见。留待真实数据证明需要后再加
- **取舍**：拆分后同一论断会产生多条 Citation 记录（claim 相同、source 不同），评测的 total_citations 会上升、存在性通过率的分母变大——这是**更真实的口径**，旧口径把多编号引用记为 1 条必然失败的引用，是双重失真

## 影响

- `validator.py`：新增 `_split_ref` 静态方法；`_extract_citations` 对每个匹配展开拆分结果
- `writer.py`：无改动（提示词维持"只能引用真实存在的编号"，多编号由 Writer 自行决定）
- 新增 `tests/test_multi_number_citation.py`：覆盖 6 个场景（英文逗号、中文顿号/和、单编号、URL 兼容、混合内容、旧 bug 对照），离线运行无 API 调用
- 与 ADR-0004 叠加后，建议跑一次 `CitationEvaluator` 真实评测，对比 17/67 基线验证两个修复的实际收益
